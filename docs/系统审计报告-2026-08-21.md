## 一、Bug（确凿的运行时缺陷）

### 🔴 P0-1 入厂登记二维码指向不存在的路由 → 扫码落到登录墙
- **证据**：
  - `frontend/src/pages/EPermits/Detail.tsx:537` — 培训签到二维码生成 `${window.location.origin}/public/worker-register?token=...`
  - `frontend/src/pages/EBoard/Board.tsx:559` — 看板二维码同样生成 `/public/worker-register`
  - `frontend/src/App.tsx:62-63` — 前端路由只有 `/public/entry/:token`（EntryVerification）和 `/public/entry-register`（EntryRegister），**没有 `/public/worker-register`**
  - `App.tsx:352` — `<Route path="*" element={<Navigate to="/" replace />} />` 通配兜底
- **影响**：承包商/工人扫码 → SPA 通配重定向到 `/` → 进入登录页（需登录）。整条"扫码入厂登记"链路实际走不通，且 `?token=` 在 EntryRegister 中未被使用（该页直接拉取全部进行中任务，未绑定具体作业票）。
- **解决**：
  1. 把两处二维码路径统一改为存在的路由，如 `/public/entry-register`（或给该页增加带 token 的专用路由 `/public/register/:token`）；
  2. EntryRegister 解析 `token` 并按 token 限定可登记的作业任务（当前是"选全部任务"），让二维码与作业票绑定；
  3. 补一条 `?token=` 参数失效/过期校验（复用 actionTokens 体系）。

### 🟠 P1-2 后端 HTML 页硬编码 `localhost:5190`
- **证据**：`backend/src/modules/public-actions/public-actions.controller.ts:316` — `entryByCodePage()` 提示"直接访问 http://localhost:5190/entry"。
- **影响**：部署到服务器后，手机按提示访问的是手机自己。文档性误导。
- **解决**：改用 `appBaseUrl()` 拼接（该文件已有 import 习惯，只需替换常量）。

### 🔴 P0-3 `ensureAdmin()` 每次启动强制重置 admin 密码
- **证据**：`backend/src/database/seed.service.ts:903-909` —
  ```
  } else if (existing.passwordHash !== wantHash) {
    await this.db.update(schema.users).set({ passwordHash: wantHash, mustChangePassword: false, status: 'active' })...
  ```
- **影响**：管理员在界面改密后，**任何一次重启都会把密码还原为 `ADMIN_PASSWORD`**（默认 `Admin@123456`），且不强制改密。安全上等于"管理员口令永远等于已知默认值"（结合 .env 里就是默认值，攻击者可无难度登录 admin）。功能上管理员改密形同虚设。
- **解决**：把"救援/还原"改为"仅首次创建 + 显式开关"：
  1. 删除每次启动的比对还原逻辑；
  2. 改密不再被覆盖；
  3. 如需"忘记密码救援"，改为显式命令（如 `RESET_ADMIN_PASSWORD=1` 一次性执行）并强制 `mustChangePassword: true`，执行后自动失效。

### 🟠 P1-4 部署环境把访问令牌 TTL 从 30 分钟拉回 7 天
- **证据**：`backend/src/modules/auth/auth.service.ts:15` 默认 `'30m'`（S07 设计）；但根 `.env:15`、`.env.production:13`、`docker-compose.yml:45` 全部设 `JWT_EXPIRES_IN=7d`。
- **影响**：生产环境 Access Token 有效期 7 天，泄露窗口极大，S07 缩短令牌的目标被部署配置反向覆盖。
- **解决**：生产 `JWT_EXPIRES_IN` 设回 `30m`（或按企业策略 ≤2h）；刷新令牌 TTL 维持 7 天即可。

### 🟡 P2-5 `start-local.sh` 端口与 vite 配置不一致
- **证据**：`start-local.sh` 注释/提示前端 `http://localhost:5180`；`frontend/vite.config.ts:31-34` 实际 `preview.port=5190, strictPort:true`。
- **影响**：按脚本打开 5180 会失败。
- **解决**：脚本统一为 5190，或让 vite 回退到 5180。

## 二、安全风险

### 🔴 P0-6 admin 默认口令公开且被固化（同 P0-3）
- 默认口令 `Admin@123456` 出现在：`seed.service.ts:15/828/876`、根 `.env:16`、`.env.production:14`、`start-local.sh:12`、`deploy.sh` 注释等。结合 P0-3 的"每次重启还原"，等于生产系统 admin 口令长期等于公开默认值。
- **解决**：强制部署时随机生成 `ADMIN_PASSWORD` 并首次登录强制改密（保留 P0-3 修复后）；从文档/脚本中移除明文口令示例。

### 🔴 P0-7 公网部署无 HTTPS（明文传输令牌/Cookie）
- **证据**：`nginx/nginx.conf` 443 server 整段注释；`nginx/certs` 为空目录。
- **影响**：若按现有配置把 8010 暴露公网，登录口令、Bearer Token、HttpOnly 刷新令牌 Cookie 全部明文传输，可被中间人截获。`COOKIE_SECURE` 默认 false 进一步放大风险。
- **解决**：部署正式环境必须启用 HTTPS（云厂商免费证书 + 443 配置 + `COOKIE_SECURE=true`）。若暂不对外、仅内网，应保留内网 IP 访问并明确不暴露公网。

### 🟠 P1-8 登录限流为进程内内存实现，多实例/重启即失效
- **证据**：`auth.service.ts:214-245` `loginFailMap` 为模块级 Map，无持久化。
- **影响**：单进程 PGlite 场景可用；若未来多副本部署，限流各自独立；重启后计数清零。
- **解决**：单实例可接受；若上多副本，改用 Redis/DB 计数。当前可保留并加说明。

### 🟠 P1-9 公开接口面较大，建议审计
- 全部 `@Public`：`public-actions.controller.ts:18`（整个控制器：任务列表/登记/入场/培训/审批/签字）、`hazards.controller.ts:29/38`（匿名上报）、`files.controller.ts:39`（匿名上传，IP 限流）、`areas.controller.ts:15`。
- 其中 `GET /api/public/worker-register/tasks` 匿名返回全部进行中作业任务（地点/承包商/作业名称），可被爬取。
- **解决**：任务列表接口加低频限流 + 仅返回必要字段；公开 token 类接口统一校验 token 有效性/过期（确认已做）；文档化公开接口清单。

### 🟡 P2-10 弱密码策略
- `auth.service.ts:252` 新密码仅 `length >= 6`，无复杂度/历史校验。
- **解决**：至少 8 位 + 含字母数字（可加数字+字母组合校验）。

### 🟡 P2-11 密钥明文落盘但未进 git
- 根 `.env` / `backend/.env` 明文 JWT_SECRET / DB_PASSWORD / ADMIN_PASSWORD；`backend/.env` 的 `JWT_SECRET=ehs_local_dev_secret_2026_change_me_please` 为弱默认。虽然 `.gitignore` 忽略 `.env`，但多份部署包（ehs-win-deploy/backend.env、各种 zip/tar.gz）中可能携带。
- **解决**：部署包剔除 `.env`；生产改用 docker secret / 系统环境变量；轮换当前已知密钥。

## 三、设计不合理

### 🔴 P0-12 作业票"双模型"并行（S15 遗留）→ 大量重复实现
- **证据**：`work-permits.service.ts`（1779 行）+ `work-permit-applications.service.ts`（1348 行）+ 4 个 controller（work-permits/e-permits/work-permit-applications/e-applications，共 1071 行）。两套都在做审批链、邮件通知、签字 token、二维码、入场登记。S15 已因此出过一次"启动即删光电子票"的 bug。
- **影响**：同一业务两处维护，极易再次不一致；改动成本翻倍。
- **解决**（建议分阶段）：
  1. 近期：把 `work_permits` 设为唯一事实来源，`work_permit_applications` 降级为"申请草稿"薄表，申请单审批直接驱动电子票状态（已有 `autoApproveFromApplication`/`autoSubmitFromApplication` 雏形）；
  2. 中期：合并 controller 与 service，删除另一套重复方法；
  3. 远期：`drizzle` 迁移合并两表或只保留一张。
- 注意：这是**渐进收敛**，不要一次性破坏性合并（延续 S15 非破坏原则）。

### 🟠 P1-13 三套"建表/迁移"机制并存
- `drizzle-kit push`（`backend/Dockerfile` CMD 每次启动执行）｜应用内幂等 SQL（`database.module.ts:74-…` onModuleInit）｜`drizzle/0000_cynical_hammerhead.sql` 主迁移 + 各 service 内裸 `CREATE TABLE`（如 `lottery.service.ts:38` 的 `lottery_records`，**不在任何 schema 中**）。
- **风险**：schema.ts 与手工 SQL 若漂移，`drizzle-kit push` 可能对生产库产生意外 DDL；游离表不被 Drizzle 管理。
- **解决**：选定一种机制——推荐"应用内幂等 SQL"（当前实际唯一有效路径），停用 Dockerfile 的 `drizzle-kit push`；把 `lottery_records` 等游离表纳入 schema.ts；`drizzle/0000_*` 归档为只读基线。

### 🟠 P1-14 后端内嵌 HTML 页面与 React 前端重复实现
- `public-actions.controller.ts` 用模板字符串渲染 审批确认页/手机签字页/培训学习+考试页/入场签到页（含大量内联 JS）；前端另有 `PublicSign.tsx`、`Training/Exam.tsx`、`EntryVerification.tsx`、`EntryCheckIn.tsx`。
- **影响**：两套考试/签字实现，样式与逻辑可能漂移（例如培训考试的后端 HTML 用 `innerHTML` 注入题目，若题面含 HTML 有存储型 XSS 隐患）。
- **解决**：统一走 React 前端页面（SPA 路由），后端公开接口只返回 JSON；删除模板字符串页面。短期至少把 `entryByCodePage` 等仍硬编码 localhost 的页面收口。

### 🟠 P1-15 前端作业票列表/审批页高度重叠
- `/e-permits`（EPermitList）、`/work-permits`+`/hazard-work-permits`（UnifiedTicketList）、`/e-applications`（EApplicationList）、`/e-approval`（EApprovalList）、`/e-permits/review`（EPermitReview）、`/e-permits/my`（EPermitMy）——6 个页面承担列表/审批职责，入口混乱。
- **解决**：收敛为 2-3 个入口：统一列表（可切换常规/危险）、统一审批台、我的作业。逐步下线多余页面。

### 🟠 P1-16 三层 Web 服务器冗余
- `docker-compose.yml` 的 `frontend` 容器已内置 nginx（`frontend/Dockerfile`），外层再套 `ehs_nginx` 反代，而后端还能直接托管 dist（`main.ts:49-51`）。
- **解决**：保留一条链路即可——建议"顶层 nginx 反代（静态 dist 直接挂载或由 backend 单端口托管）+ API"。删除重复 nginx 层。

### 🟠 P1-17 两套 `.env` 来源不一致（配置漂移）
- 根 `ehs-system/.env`（docker-compose/deploy 用，APP_BASE_URL=47.100.60.182:8010，JWT_SECRET=生产值）vs `backend/.env`（NestJS ConfigModule 实际读取，APP_BASE_URL=localhost:5190，JWT_SECRET=本地弱值，SEED_DEMO=1）。改一处另一处不同步，极易把生产配错。
- **解决**：收敛为单一来源（建议以 `backend/.env` 为唯一运行时配置，docker-compose 环境变量通过它注入）；或让 docker-compose 显式 `env_file` 指向同一文件，并加注释说明。

### 🟠 P1-18 PGlite 本地数据放系统临时目录 + 单写实例约束
- `backend/.env` `PGLITE_DATA_DIR=D:/Users/.../Temp/ehs-pglite-v4`，注释自述"系统清理临时文件时会丢失"；且已发生过 58P01 并发损坏（`.pglite-data-v3.CORRUPT-*` 残留为证）。
- **影响**：本地预览数据随时可能丢；多进程并发起后端会损坏库。
- **解决**：本地开发换固定目录（如 `ehs-system/.pglite-data`）并保证单实例；在 README/脚本中强制"先杀旧进程再启动"。

### 🟡 P2-19 邮件功能默认关闭
- `email.service.ts:28` `enabled:false`，需在"设置→邮件"配 SMTP 才启用。审批邮件通知默认静默不可用。
- **解决**：设置页加"未配置时提示"，README 标注；如需立即通知可引导配置。

### 🟡 P2-20 PWA 离线仅 localhost/HTTPS 生效
- `frontend/src/main.tsx:26` 限定 HTTPS 或 localhost 才注册 SW；公网 HTTP（IP:8010）部署时 SW 不注册。
- **解决**：上线 HTTPS 后自然生效；如长期 HTTP 内网可放宽 hostname 判断。
